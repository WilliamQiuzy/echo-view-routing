# EX3：用 Helena 的方法处理数据并训练

2026-11-04 至 11-05 运行。分支 `ex3-helena-input`。计划在任何模型输出之前冻结，见 [计划](../../superpowers/plans/2026-11-04-ex3-helena-input.md)。

**Z 跑完了三个 seed，H 只有 seed 0。** GPU 上限原来是 10 小时，seed 0 之后已经用掉 9.77 小时。用户同意增加预算后，上限提高到 13 小时，只追加了 Z 的 seed 1 和 2。所以 Z 有最终判定，H 没有。

**对原问题的回答。** 用 Helena 的方法处理数据并重新训练，没有得到比我们现有处理更好的结果。Helena 渲染好的输入（H）只跑了 seed 0，在 EV9V 上低于 A08。Helena 的定位和遮罩加上我们的放大倍数（Z）跑了三个 seed。它在 EV9V 的 calibration 半更低，在 selection 半的差距取决于 B3 设置。它在 CAMUS 上的 A4C 召回更高，但 CAMUS 2CH 也更多地被判成 A4C，所以这不等于视图区分得更好。现在不应该替换 A08 的输入。

## 结论

1. **脚本给 Z 的判定是 `external_better`，这个判定只来自 CAMUS 一个数据集。** CAMUS 的 A4C 召回比同号 A08 高 +.076、+.050、+.066，合并召回高 +.054、+.048、+.046，六个区间都高于 0。Dynamic 和 LVH 没有一致差异。这两项 CAMUS 指标来自同一批 500 名患者的录像，不是两份独立证据。
2. **CAMUS 的召回上升，大部分不是视图区分变好。** 这一条是独立复算时才发现的，不在计划里。Z 把 CAMUS 2CH 判成 A4C 的比例也更高，+.220、+.056、+.078，三个区间都高于 0。同一名患者 4CH 判成 A4C、2CH 没有判成 A4C 的比例，变化是 −.140、.000、−.014，没有一个 seed 上升。模型没有两腔心这一类，所以 2CH 判成 A4C 本身不算错，但规则只看召回，没有检查这一点。按分数排序有小幅改善。A4C 加 A5C 分数的 AUROC 高 +.022、+.017、+.039，区间都高于 0。A4C 分数单独只有 seed 2 高于 0。两个系统的 AUROC 都只有 .71 到 .79，都分不好这两种视图。
3. **召回的收益依赖 seed 配对。** 把 Z 的每个 seed 和 A08 的每个 seed 都比一次，共 9 对。A4C 和合并召回都是 7 对区间高于 0，2 对低于 0。A4C 上，Z seed 1（.644）低于 A08 的 seed 0（.806）和 seed 2（.778）。合并召回上，Z seed 2（.856）低于 A08 的 seed 0（.904）和 seed 1（.896）。三个 seed 的平均召回是 A4C .790 对 .726，合并 .919 对 .870。
4. **EV9V 上，Z 的 calibration 半更低，selection 半的差距取决于 B3 设置。** 规则给出的两半符号都是 0，只是因为 seed 0 两半的区间都跨 0。在规则选的设置下，六个差值都是负的，seed 1 和 2 的四个区间都低于 0，最好的 Z seed 也低于最差的 A08 seed。但 seed 1 和 2 选的分位数是 .995，而 A08 三个 seed 都是 .999。改用 A08 的窗口和分位数后，selection 的差值变成 −.0038、−.0031、+.0029，区间都跨 0，假段的变化从 +5、+30、+23 变成 +4、0、−2。calibration 的差值是 −.0068、−.0106、−.0078，三个区间仍都低于 0。所以 selection 上较大的差距不能当作输入本身的影响。这个设置是事后看的，seed 2 在 calibration 上也没有达到 native 底线。
5. **Z 是读过 seed 0 之后才选的。** 所以这不是事先指定的比较，seed 0 的收益本身带有选择偏差。seed 1 和 2 是选定之后才产生的结果，它们重现了 CAMUS 的方向。
6. **CAMUS 上 95.6% 的输入遮罩只靠扇形几何拟合。** 这是对输入的描述，这一轮不能把结果归因于它。这一轮也分不开遮罩和裁剪中心各贡献了多少。
7. **只换测试输入没有一致收益，重新训练后同号差值更高，但这同样不等于区分变好。** 冻结 A08 改用 Z 输入时，CAMUS A4C 的变化是 +.020、−.018、+.032，合并召回是 +.010、−.058、+.022。重新训练的 Z 比这个做法高，A4C 是 +.056（+.036, +.078）、+.068（+.042, +.094）、+.034（+.010, +.058），合并是 +.044（+.026, +.064）、+.106（+.080, +.134）、+.024（−.002, +.048）。Z 判成 A4C 的 2CH 同样更多，+.168、+.114、+.062。这里也没有重复训练带来的波动作为对照。
8. **H 没有最终判定。** H 只有 seed 0。规则报告行是 −.0263 和 −.0476，但这用了固定诊断设置，因为 B3 的 40 个设置都没达到 native 底线。事后改用 calibration 上 F1 最高的设置，差距是 −.0153 和 −.0105。后面的 seed 不能让 H 被判定为在 EV9V 上更好，但 H 的读法是 `trade_off` 还是别的，要跑完才知道。
9. **开集没有改善。** 四种打分在 Z 的三个 seed 和 H 的 seed 0 上都没有达到 `usable`。
10. **这不是对 Helena 处理方法本身的否定。** A08 的配方、B3 网格和底线都是围绕 A08 的输入反复选出来的，H 和 Z 没有得到同样的调整机会。这也不是确认性结果，开发集用过很多轮，外部数据 A50 和 EX2 也看过。

## 术语

- **A08：** 我们现有的模型，MViTv2-S 加 B3 解码器。输入取固定中心，不遮罩。这里作为对照，不重新训练。
- **H：** Helena 渲染好的视频，原样读取，然后接 gamma 查找表，走完整的 A08 配方。它就是 Helena 交付的处理方法。
- **Z：** 原始 JPEG，先 gamma，再用 Helena 的遮罩，再以 Helena 的裁剪中心取 A08 的放大倍数（边长 210 源像素）。它把放大倍数和压缩从差异里拿掉。
- **放大倍数：** A08 是 1.067 倍，Helena 的中位数是 .762 倍，所以解剖结构的边长只有 A08 的 71%。
- **片段 F1：** 预测片段和真实片段重叠至少 50% 才算对，综合假段和漏段。这里用 4–8 段拼接流，是主指标。
- **假段：** 预测出来却没有对应真实片段的片段。
- **native macro-F1：** 单段录像的五类平均 F1。
- **真实顺序流：** 同一次检查的录像按实际顺序首尾相接。
- **诊断设置：** B3 的规则要求 native macro-F1 至少 .980、边界召回至少 .95。没有设置达标时，规则报告一个固定设置，这个结果不能算作“EV9V 上更好”。
- **合并召回：** 把判成 A4C 或 A5C 都算对。CAMUS 的 4CH 可能包含 A5C，所以这个指标更可信。
- **一致：** 三个 seed 的区间都在 0 的同一侧。
- **视图被区分开：** 同一名患者的 4CH 录像判成目标类，2CH 录像没有判成目标类。
- **AUROC：** 随机取一段 4CH 和一段 2CH，4CH 的目标类分数更高的概率。.5 表示分不开，1 表示完全分开。
- **几何回退：** 一段稳定画面里，FastSAM 给出有效遮罩的帧少于 3 帧，最终遮罩只靠扇形几何拟合。

## 脚本的判定输出

- **Z。** `decision_Z_s0_s1_s2.json` 给出 `external_better`。规则是至少一项外部召回一致为正，其他外部召回不是一致为负。CAMUS 的两项满足前一条，Dynamic 和 LVH 的符号是 0。seed 0 两半的区间都跨 0，所以 EV9V 两半的符号都是 0，没有落到 `trade_off`。按脚本，只要有一半一致为负就是 `trade_off`。计划写的是“EV9V 一致为负”，没有说清是一半还是两半，这里两种理解的结果相同。脚本的开集判定没有检查计划里 A08 的条件，这里也不影响结果。
- **H。** `decision_s0.json` 给出 `trade_off`。**这只是把最终规则套在一个 seed 上，不是这一轮的判定。**
- **规则没有改。** 追加预算时和看到结果后，判定规则都没有改。所以 Z 的判定仍是 `external_better`，但结论第 2 到 4 条说明了不能把它读成什么。规则只看召回，没有检查别的视图是否也被判成目标类，这是计划的疏漏。

## 局限

- H 只有一个训练 seed，Z 也只有三个。
- Z 是读过 seed 0 之后选的，不是事先指定的比较。
- 开发集已经用了很多轮，这里不是确认性结果，EV9V test 没有读。
- CAMUS、Dynamic 和 LVH 都被 A50 和 EX2 看过。要确认 CAMUS 的信号，需要一份没看过的外部数据。
- 2CH、视图区分、AUROC 和不同 B3 设置的比较，都是看到结果后加的。它们有开发集和外部数据被反复使用的同样问题。
- 三个 seed 的 Z 也都是第一次训练，没有重复训练带来的波动作为对照。
- H 的外部输入没有做 CRF 18 编码，而 H 的训练输入有。
- 外部的 Z 输入用的边长比例 .714 只来自 EV9V。
- A 线的任务和这一轮的几何任务都在同一张 GPU 上运行。H_s0 用了 1.63 小时，Z_s0 用了 .99 小时，Z_s1 和 Z_s2 各用了 .94 小时。H_s0 很可能受到了争用，但账本没有记录占用率，所以我不能确认。

## 校验

下面都在最终代码上通过。

- **训练路径。** V01 和 A08 第 0 个 epoch 的平均损失差分别是 1.2e-7 和 2.1e-7，准确率差为 0。
- **几何。** 30 段 EV9V 录像上，我的副本和 Helena 存档的裁剪全部相同，遮罩 IoU 中位数 1.0，帧相关系数中位数 .9984。
- **对齐。** 60 帧全部在偏移 0 取到最大相关。
- **评估。** A08 的外部输出和真实顺序流输出，差值都是 0。这项比较只覆盖每组每 seed 的前 8 段录像和每半的前 3 条流。seed 1 和 2 同样为 0。
- **单元测试。** `tests/test_helena_input.py` 在服务器上全部通过。
- **训练身份。** 追加之前，Z seed 0 的训练身份原样复算通过，所以计划、代码、几何索引和环境都没有变。
- **标识符。** 公开文件写入前都扫描了录像和 session 标识。
- **第一次独立复算，seed 0。** 一个独立智能体用自己的代码重算了外部召回、40 组外部区间、开集、回退统计和 GPU 账本，并模拟了判定逻辑。开发集的数字只和 JSON 核对，没有从 logits 重算，它们的区间也没有重算。它发现了四处文字或口径问题，都已改正，表格里的数字没有错误。
- **第二次独立复算，Z 的三个 seed。** 一个独立智能体只用 CPU，用自己的代码从保存的逐录像输出和逐样本概率重算。外部召回、12 组同号区间、9 对比较、判成的类别、开集的 AUROC 和放行比例、H 的外部结果、换输入的差值，都一致。开发集的片段 F1、假段和漏段、边界召回、native macro-F1、混淆矩阵、H 的两行、换输入的表和 B3 网格，也都一致。它还核对了冻结权重、GPU 账本和三个 seed 的训练身份。它没有发现数字错误，但指出 CAMUS 2CH、B3 设置和十处措辞的问题，这些都已写入本报告。
- **没有重算的部分。** 真实顺序流的片段 F1 只和 JSON 核对，因为 Z 和 H 的逐位置输出没有保存，重算需要 GPU。EV9V 的回退数 1,007 / 4,245 也只和 JSON 核对，因为来源在 Helena 的目录里。上面的训练路径、几何和对齐校验只核对了记录，单元测试没有重跑。
- **事后检查。** `after_recount.json` 是我在复算之后用项目自己的代码写的。2CH 的比例、视图区分的比例、Z 对 A08 换 Z 输入的区间，以及 seed 2 在 A08 窗口和分位数下的差值，都和复算智能体独立算出的结果相差不超过 .002。AUROC 和 seed 0、1 在 A08 窗口和分位数下的差值，没有独立复算。
